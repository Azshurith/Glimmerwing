# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Glimmerwing is a browser split-screen versus shooter in TypeScript (canvas, no framework). Two fairies each fly in their own meadow; chains you set off in your meadow send attacks into your rival's. The gameplay borrows mechanics from Twinkle Star Sprites (charge levels, Extra Attacks, reverse attacks, boss cycles, damage rules); code comments call it "TSS". Everything in the game is original: art, names, characters and sounds.

## Commands

```
npm run build        # typecheck, then esbuild bundles everything into one file, dist/index.html
npm run check        # typecheck + eslint + prettier --check: run before committing
npm run lint:fix     # eslint --fix
npm run format       # prettier --write .
npm run dev          # build, then serve on http://localhost:8787 (relay at /ws)
npm run server       # serve the existing dist/ only
make project_start   # Docker: the game, MariaDB and phpMyAdmin (make project_setup first makes .env)
```

There is no test suite. To verify a change, run `npm run check` and play the build. `npm run build` bundles straight to `dist/index.html`, so after a build you can open that file directly.

**Docker and the database.** Laid out like the user's other projects: `.docker/<Service>/Dockerfile` (Node, MariaDB, PhpMyAdmin), `.env` (from `.env.sample`, not committed) and `docker-compose.yml`, with a `Makefile` of `project_*`, `node_*` and `db_*` targets. The `node` container mounts the repo, runs `npm install && npm run dev` with its own `node_modules` volume, and gets the database as `DB_*`.

**The server** is TypeScript in [server/src/](server/src/) (its own [server/tsconfig.json](server/tsconfig.json): `@/…` is the game's `src/`, `@server/…` the server's; decorators on), bundled by `build.mjs` with the game's simulation inside as `dist/server.cjs` and `dist/verify-worker.cjs` (CommonJS; `express`, `typeorm`, `mysql2` and `reflect-metadata` stay in node_modules), and run by `npm run server`. `npm run build` typechecks only the game, so `npm run typecheck:server` (part of `npm run check`) checks the server. [main.ts](server/src/main.ts) starts it all; [app.ts](server/src/app.ts) is the Express app (the built page from `dist/`, `/health`) and [api.ts](server/src/api.ts) the `/api` router (routes listed at its top; Express 5, so a handler can just throw an `HttpError` or reject). **The database is TypeORM over MariaDB** when `DB_HOST` is set ([database/data-source.ts](server/src/database/data-source.ts), `openDatabase`); without one the API answers 503 (there's no in-memory store any more). The schema is the migrations' ([database/migrations/](server/src/database/migrations/), raw MariaDB SQL, run in order at start-up and recorded in the `migrations` table; `synchronize` is off, so a schema change is a new migration and the entities in [database/entities/](server/src/database/entities/) must match it, with every column's `type` spelled out as esbuild emits no decorator metadata). **Every table ends with `created_at`, `updated_at`, `deleted_at`** (`Timestamped` in `entities/columns.ts`; soft deletes: repositories leave deleted rows out by themselves, and the raw queries in [store.ts](server/src/store.ts) say `deleted_at IS NULL`). JSON documents are LONGTEXT `CHECK (JSON_VALID)` columns read through `asJson`/`fromJson` (mysql2 may hand them back parsed already); BIGINTs through `asNumber`. A player's own tables are `players_progress`, `players_settings`, `players_matches`, `players_runs` (Endless) and `players_replays`; chat is `chat_messages` (by `channel`, 'world' for now). **The catalog**: `characters`, `maps` and `types_modes` (each with `is_enabled`), each numbered by the database (`id`, INT AUTO_INCREMENT) with the game's own id as a unique `code` ('pip', 'forest', 'cpu'), filled from the game's `FAIRIES`, `MAPS` and modes at every start ([catalog-seed.ts](server/src/catalog-seed.ts), `INSERT IGNORE`, so a row switched off stays off); the player tables point at them by foreign key (`mode_id`, `map_id`, `fairy_id`, `rival_fairy_id`). **Art lives in the database too**: `characters.sprite_sheet` (the PNG, MEDIUMBLOB) and `sprite_atlas` (the `SpriteSet` layout as JSON: `cw`, `ch`, `bodyX`, `bodyY`, `scale`, `anims`), `maps.monster_sheet`, `monster_cell` and `monster_overlay_row`, and the `monsters` table (one row per monster on a map's sheet: `map_id`, `code` the kind, `name`, `role` plain/big/shelled/spinner, `sheet_row`). [art-seed.ts](server/src/art-seed.ts) fills an empty sheet from the bundled files at every start (`assets/<SpriteSet.file>`, `assets/monsters/<map>.png`) and adds missing monsters, leaving anything already there alone. `GET /api/catalog` carries the layouts and versions (`art`, versioned by the row's `updated_at`) and `/api/art/characters|monsters/<code>.png?v=` the pictures (cached for good); [src/data/server-art.ts](src/data/server-art.ts) (`useServerArt`) swaps a fairy's `sprite` or a map's sheet (`useServerMonsters`, which `monstersFor` prefers) in once its picture has loaded and checks out, so the page keeps its bundled art offline or until then. Art is only drawing: it never touches a round. The API and the game only ever see codes: `Catalog` (in memory) turns them into ids for the store's inserts and back (`characterId`/`characterCode` and so on), and the store's raw queries join the catalog tables for them. Switching a fairy, map or mode off (`is_enabled = 0`, or soft-deleting the row, e.g. in phpMyAdmin) takes effect on the server within 15 s ([catalog.ts](server/src/catalog.ts) rereads it): `GET /api/catalog` tells the game (at start and again each time the lobby is opened from the title; `src/data/availability.ts`, kept in localStorage: `fairyAvailable`/`mapAvailable` inside `Game.isUnlocked`/`mapOpen` show a fairy or map as locked and "Unavailable", `modeAvailable` greys out a mode on the lobby's picker with OFF and makes `?mode=` open nothing), the verifier refuses games with it, and online matches refuse the pick and deal no round on that map; with `online` off the relay turns away every quick match, room and join. The API knows guests by a bearer token whose SHA-256 is stored. **The server decides progress**: a browser never sends its own trophies, unlocks or records. A finished VS CPU, 2 Players or Endless game goes to `POST /api/results` as its replay; [server/src/verifier.ts](server/src/verifier.ts) plays it through again in a worker thread ([verify-worker.ts](server/src/verify-worker.ts)) with the game's own simulation, [src/server/verify.ts](src/server/verify.ts) (`verifyReplay`: the player's tape for their meadow, the CPU deciding for itself from the round's seed, the player's fairy and stage must be open on the server's record and switched on in the catalog, the rounds must end exactly where the recording says), and only its own result counts (each `players_matches`/`players_runs` row points at its replay by `replay_id`): [src/game/rewards.ts](src/game/rewards.ts) (`applyOutcome`, shared with the game) adds it to the stored progress, and the match history, the Endless leaderboard and the replay are written; one game is never counted twice (`players_replays.recorded`), and one player's results are counted one at a time (`Turns`). In the game, [src/game/account.ts](src/game/account.ts) (`Account`, `Game.account`, started by `Game.connectAccount` from `main.ts`) makes the guest, takes the server's progress on start and after every counted game (`onProgress` → `Game.adoptProgress`; the game shows its own `applyOutcome` reckoning at once in the meantime), keeps games finished while the server can't be reached in localStorage and sends them later (`submit`, `flush`), syncs settings (the newer copy wins, `SyncStamps`) and fetches the Endless leaderboard for Profile.  Online matches are run by the server itself, which counts them for both players (see Online). localStorage stays the first place everything is saved, so the game is the same offline; [src/net/api.ts](src/net/api.ts) finds the API beside the relay, and a page opened from a file with no server has none. The service worker never caches `/api`.

`GW_SERVER=wss://host/ws npm run build` bakes in the online relay address (it becomes `__GW_SERVER__` through esbuild `define`). The page can also take `?server=…`.

## Workflow

Do each feature on its own branch (`feature/<name>` or `fix/<name>`) and open a pull request against `main` when it's done.

## Architecture

**Build.** [build.mjs](build.mjs) bundles `src/main.ts` as an IIFE and puts it in place of `/*__BUNDLE__*/` in [index.template.html](index.template.html). The game page is only the game, filling the window; how to play, controls, mode links and reset progress are on a second page, [guide.template.html](guide.template.html), copied to `dist/guide.html` (the title screen's `?` button links to it, and `index.html?mode=cpu|versus|online` opens the game in a mode). Images get imported as data URLs, so the game is a single self-contained HTML file. The build also writes a PWA manifest, the icons, and a service worker whose cache name is a hash of the page.

**Loop.** [src/main.ts](src/main.ts) wires up the page (fitting the canvas to the screen, fullscreen, wake lock, mute) and runs the fixed-step loop: `game.step(C.STEP)` at 60 Hz with an accumulator, then `game.draw()`; while frames run late (a Fever volley on a phone) [src/render/resolution.ts](src/render/resolution.ts) (`AdaptiveResolution`) lowers `renderer.resolution`, so the canvas draws fewer pixels, and raises it again once they keep up. The view is 504×320 with the meadows side by side, scaled up to fit. On a wide landscape screen a local round plays in wider meadows so the view fills it edge to edge: `main.ts` works out `renderer.fieldWidthToFill` from the screen's shape, and `Game.newRound` sets it with `C.setFieldWidth` (`FIELD_W` and `VIEW_W` are `let`s, up to `FIELD_W_MAX`; read them through `C.` so you see the current width, never copy them into a module-level constant). Online rounds, the menus and the tall layout always use `FIELD_W_BASE`. Likewise `FIELD_H` (`C.setFieldHeight`): a vs-CPU round on an upright phone with the Settings option *Hide the rival's meadow* (`settings.ts`, saved in localStorage; Settings in the main menu opens the panel in `index.template.html`) plays in taller meadows reaching the top of the screen, the rival's meadow and console drawn off screen and a slim `soloBar` across the top instead. The title, menu, Characters, Profile and select screens fill a wide landscape screen another way: their view widens to its shape (`renderer.menuW`, up to `WIDE_W_MAX`) with their content centred (`renderer.viewX`; `Renderer.begin` translates by it and `Input` takes it off touches) and their sky, bars and hero art reaching out to the edges (`bleed`). On a portrait screen, while one player is in a round, `Game.draw` switches the renderer to a tall layout (`TALL_*` in config): your meadow full width against the bottom edge, and the rival's at half size above it beside a compact console. Moving from one menu screen to another (the lobby to Settings, Profile, Maps or Characters, and back; not a round's own phases or a replay) fades the old screen quickly away while the new one builds itself up in stages ([src/render/transition.ts](src/render/transition.ts): `ScreenTransition` keeps a copy of the old screen, which `main.ts` takes before drawing the new one; each screen draws its parts inside `enter(ctx, part, draw)`, so the heading bar (`'bar'`) and buttons (`'buttons'`, popping in one after another) come first, the background (`'bg'`) rises out of the dark, then the panels (`'panels'`) slide and fade in, from the right going deeper and from the left going back, and the hints (`'hint'`) last; none for players who ask for reduced motion), and the page's panels come in with it (chat slides in from the left, Settings rises in with the panels). `main.ts` refits the page whenever the layout changes, stretches the tall view to the screen's shape (`renderer.tallH`, up to `TALL_H_MAX`; and down to `TALL_H_MIN` on a squatter screen: in a round the band above your meadow shrinks, and the title and select screens shrink as a whole, see `screens/menu-fit.ts`), and the page always fills the window; real fullscreen (which hides the browser's bars) and sound are switched in Settings (M also toggles sound), never by a tap.

**Game ↔ Field.** [src/game/game.ts](src/game/game.ts) (`Game`) owns the phases (title → modes → select → countdown → playing …: the title screen offers *Sign in with Google*, greyed out until it exists, and *Play as guest*; `modes` is the lobby, the main menu ([src/render/screens/lobby-screen.ts](src/render/screens/lobby-screen.ts)), laid out like an arena game's home screen but drawn like the other menu screens (their night sky, `Backdrop`, with its light rays turning behind the island; the dark heading bar over a gold line, mirrored for the bar along the bottom; slanted navy panels in thin gold edges, `LobbyScreen.panel`; gold arcade arrows beside the mode button), with the furthest stage open on the trophy road (`Game.lobbyMap`) floating in the middle as an island (an `'islands'` map's top is a meadow painted in its colours, `meadowTop`; a `'ground'` map's top is its own scenery, squashed into the oval; cliffs in its `cliff` colours below) and the mode button under it (`LOBBY_MODES`: Story Mode, greyed out for now, VS CPU, Endless, Online Play, 2 Players; ◀ ▶ change it, Enter or a tap plays it, a mode switched off on the server shows as such); the player's avatar in their frame, wins and counters across the top; quick buttons at the top left (`LOBBY_QUICK`: History and Ranking open Profile's tabs, Guide the guide) above a card for the next stage on the trophy road; the other screens on a bar along the bottom (`LOBBY_NAV`: Characters, Maps, Profile, Settings; ▼ moves the cursor there); World chat's latest lines at the bottom left and friends down the right (a tab on the right edge on a phone; an empty list until friends exist). T or a tap on the ticker toggles the chat panel (`Game.chatOpen`), the page's `#chat` ([src/page/chat-panel.ts](src/page/chat-panel.ts), the whole height of the screen at the left (the whole screen on a phone), placed by `--chat-*`, which `main.ts` sets from `lobbyLayout`): World chat, polled from `GET /api/chat/world` every few seconds while the lobby shows, sent with `POST /api/chat/world` (the server cleans and masks it, `server/src/chat-filter.ts`, and limits how fast a player posts; the `chat_messages` table), with tabs for Friends, Lobby and Guild chat still to come. Each message shows its writer's look ([src/data/looks.ts](src/data/looks.ts), `PlayerLook`: an avatar, the face of any fairy they've unlocked, painted for the page by `render/avatars.ts`; a frame round it and a chat bubble, from `FRAMES` and `BUBBLES`, some opening on the trophy road; their CSS is made from the data by `lookStyles`), which the chat panel's Style picker changes (`Account.look`, `PUT /api/me/look`, checked by the server against the player's record; kept on `players.avatar`, `avatar_frame`, `chat_bubble`); the emblems on the mode button and the bar are `screens/emblems.ts`; Characters is the `roster` phase ([roster-screen.ts](src/render/screens/roster-screen.ts): each fairy's portrait, stats, skills and unlock, and a live demo meadow; in landscape the portrait sits against the left edge, the demo against the right and the stats between, spread over the widened view by `spread(bleed)`, while on a phone held upright the demo opens full size in a pop-up from a PREVIEW button on the portrait (`Game.demoOpen`): [src/game/preview.ts](src/game/preview.ts) (`SkillPreview`) runs a real `Field` with a scripted pilot showing her plain shot, charge shot and bomb on a loop, its outbox and sounds dropped), Maps the `maps` phase ([maps-screen.ts](src/render/screens/maps-screen.ts): each stage's name, trophy lock, `Stage.blurb`, difficulty and its five monsters by role (`MonsterSheet.names`), beside a live meadow on that map flown by [src/game/map-preview.ts](src/game/map-preview.ts) (`MapPreview`), whose fairy never shoots so each formation plays out whole, captioned with its shape, movement and re-form from `Field.latestFormation`) and Profile the `profile` phase ([profile-screen.ts](src/render/screens/profile-screen.ts): two tabs, Record (the record and unlocks) and Match History (`Game.history` from `GET /api/me/history`, plus this browser's own last game if the server lacks it), where a game opens the `matchinfo` phase ([match-screen.ts](src/render/screens/match-screen.ts), three tabs: Overview, the result, both fairies, the score and its numbers, with Watch Replay and Copy Link; Scoreboard, each side's numbers side by side and the rounds; Graphs, the match over time (advantage with its big moments marked, hearts, pops, attacks sent). Scoreboard and Graphs come from [src/game/match-stats.ts](src/game/match-stats.ts) (`matchStats`), which plays the game's replay through once more, silently, counting each meadow's sounds and sent attacks and sampling both sides every second; `fromSide` turns an online match, recorded in seat order, to the player's side))), rounds, match flow, the CPU pilot and the online session. Each meadow is its own `Field` ([src/game/field.ts](src/game/field.ts), the largest file), and the two fields never reference each other:
- A field pushes outgoing attacks to `field.outbox`. `Game` moves them into `transits`, then hands each one to the other side's `field.receive()` after its flight time.
- A field pushes sound requests to `field.sfx`. `Game.drainSfx()` plays them with stereo pan and volume chosen by side and mode.
- Fireballs (TSS Normal Attacks, attack kind `'star'`): `Field.resolveChain` sends `fireballsFor(hits)` of them (`feverFireballsFor` in Fever), each sized by the combo hit that sent it. Fireballs look the same on both sides (`fireLook`): orange as sent, purple once shot back, flashing every colour once shot back a second time (Fever skips purple: a Fever fireball, or any fireball shot back by a player in Fever, goes straight to its last reflection, so breaking it again sends the Extra Attack); shot back `FIREBALL_MAX_REFLECTS` times and broken again, it becomes an Extra Attack. A Normal flies the route `normalRoute` ([src/game/fireball-path.ts](src/game/fireball-path.ts)) works out when it's sent, from where the chain ended (never above `FIREBALL_TOP_Y`, under the HUD bar) toward the rival's fairy (`Field.rivalFairy`, plus `aim`, a volley spread `FIREBALL_AIM_SPREAD` apart): it takes one of two at random (`FIREBALL_STRAIGHT_CHANCE`), wherever it's sent from: straight up to the top line (or along at its own height if it's already near the top), straight across into the rival's meadow and straight down once over the fairy; or a diagonal climb, a bounce off the top border near the middle of the screen and a diagonal descent into the rival's meadow at the fairy. `Game` flies the part up to the rival's near wall (`Outgoing.route`); `Field.receiveFireball` takes it in as a `'drop'` from `Outgoing.enter` on a line it keeps to (it never follows her once in), at `FIREBALL_TRANSIT_SPEED` times a speed of its own picked when it's sent (`FIREBALL_NORMAL_SPEED_MIN`–`_MAX`, carried in `boost`) all the way (slower in Fever, by its `pace`) and on the tempo between the meadows as in them (`Field.attackPace`), never set by size; each reflection gives it a set speed, `FIREBALL_FALL_SPEED` times `SPEED_REVERSE` per reflection, boosted by the Perfects of whoever shot it back (capped by `FIREBALL_MAX_SPEED`); shot down it flashes, turns into a Reverse where it broke and crosses the screen on its `reverseCurve` ([src/game/fireball-path.ts](src/game/fireball-path.ts): the same two routes at random, onto where the rival's fairy was, locked from `Field.rivalFairy`), flown as `'back'` in the breaker's meadow, drawn on the same path between the meadows, and finished as `'cross'` in the sender's meadow, where it's a Reverse (level 2+) and then falls on out; `?debug=paths` draws every fireball's path; breaking one that's been shot back `FIREBALL_MAX_REFLECTS` times sends the breaker's Extra Attack (`'imp'`). Tuning is under `FIREBALL_*` in config.
- Endless (`mode: 'endless'`, `Game.vsCpu` covers it with VS CPU) is played alone: you pick a fairy and a map as against the CPU, and the CPU flies the second meadow, hidden and unbeatable (its hearts refill), so its chains rain attacks on you while yours go nowhere. `Game.directEndless` runs the run: no attacks for `ENDLESS_GRACE` seconds, then a growing share of them (`ENDLESS_SHARE_*`), and guardians on a schedule (`Field.summonGuardian`; first at `ENDLESS_FIRST_BOSS`, then every `ENDLESS_BOSS_EVERY` less 3 s each time, down to `ENDLESS_BOSS_MIN`). The run ends when you go down (`Game.endEndless`): the time survived and guardians weathered are saved as `Progress.endlessBest`/`endlessBosses` and shown on Profile. There's no rival in view: fairy select shows only your panel (`SelectView.solo` names the mode in place of VS), and the hidden meadow's fireballs drop in from the top (`fromAbove` strips their side-wall route). In landscape your one meadow fills the whole screen (`C.setFieldWidth(w, true)`: `VIEW_W` is then the meadow, up to `SINGLE_W_MAX`, filled from `renderer.viewWidthToFill`; ground bands are painted as wide as it), with see-through stat cards over its left and right edges (`Hud.endlessSides`: time and best; guardians, next guardian, speed); on a phone it's the solo tall layout with a slim bar (`Hud.endlessBar`).
- Both fields are built from the same round seed (seeded RNG in [src/core/rng.ts](src/core/rng.ts)), so both get identical waves. The seed also decides which meadow the Hollow Crow appears in.
- A local round is [src/game/match.ts](src/game/match.ts) (`RoundSim`): both fields, the transits between them (`transitTime`, `flightTime`, `riseSpeed`), the CPU pilot (seeded from the round's seed, `CpuPilot(reaction, seed)`) and Endless's director; each playing step is `frozen` (a moonseed hitstop), else `share`, the controls (`cpuControls`), then `advance`. `Game` holds the current one as `round` (its `fields`, `transits` and Endless numbers are getters onto it), and the server's check runs the very same class. **The simulation must play out identically in every engine**: it uses [src/core/dmath.ts](src/core/dmath.ts) (`sin`, `cos`, `atan2`, `asin`, `hypot`, `pow`, `sq`, `powi`, built from + − × ÷ and `Math.sqrt`, which are exact everywhere) in place of `Math.sin` and the like and `** 2`, which each engine computes its own way (Safari's differ from Chrome's and Node's); drawing code can use `Math`. Never `Math.random` in a round, and nothing that steps a round's fields outside `RoundSim` (a new round's meadows first move once the countdown is over).
- Replays ([src/game/replay.ts](src/game/replay.ts)): a round is fully decided by its seed and each step's controls, so `Recorder` keeps, per round, the seed, the meadow size (`C.FIELD_W`/`FIELD_H`, single or not) and both meadows' controls as run-length tapes (the CPU's too, so `CpuPilot` may use `Math.random`; touch targets go through `quantize` before the meadow sees them). Anything else in a local round that picks at random must use a seeded `Rng` (Endless's share filter uses `Game.endlessRng`), never `Math.random`, or replays drift. `Game.keepReplay` finishes it when a VS CPU, 2 Players or Endless match ends: kept in localStorage (`saveLocalReplay`) and uploaded (`Account.saveReplay`, the `replays` table). `Game.watchReplay` plays one: `ReplayPlayer` deals the seeds and feeds both meadows (`played` is the position on its timeline of playing steps, `length` and `roundStarts` its shape), nothing counts toward progress, Space/tap steps the speed (`Game.speed`, run by `main.ts`), Esc leaves; a tape that runs out early ends it (`replayRanOut`). Opening a replay first runs it through silently (`runReplayTo` with `seeking`, which mutes sounds and reads no input) to collect its highlights from the meadows' sounds (`noteHighlight`: big chains, Fever, Extra Attacks, guardians, bombs; a Perfect's `'extra'` sound has `p` 1 so it isn't one). `Game.seekReplay` jumps anywhere: forward by running ahead, back by starting over and running ahead (a full match takes well under a second). The controls along the bottom are `Hud.replayPanel` (`replayPanelLayout` is shared with the taps): a round chip per round, the timeline with round ticks and a marker per highlight (yours above, the rival's below), and a knob to drag (`Game.scrub`; `Input.pointer` follows the held pointer; letting go seeks, snapping just before a highlight it's on), and a row of buttons (previous highlight, back 5 s, pause/play, forward 5 s, next highlight, speed) so a touchscreen can do everything; their keys are [ ← P → ] and Space, and 1–9 pick a round. On an upright screen a replay always takes the tall layout: `tallPlacement(h, fit, solo)` scales a meadow recorded wider or taller than this screen's to fit and centres it (an Endless run recorded in landscape sits mid-screen under its bar); live rounds never need it. The panel's ⌄ button (or H) minimises it to a small tab with the time and a thin progress line along the bottom edge (`Game.replayMini`, remembered in localStorage); a tap on the tab (or H) brings it back.  Online matches are recorded by the server, which runs them. `build.mjs` stamps `__GW_SIM__`, a hash of `src/core`, `src/game` and `src/data`, on each replay so one from another build is flagged. Profile's Match History lists the player's games; each one's details (`'matchinfo'`) watch its replay (`Game.watchCode`, coming back to the details on Esc) and copy it as a `?replay=CODE` link.

**Online** ([src/net/](src/net/), [server/src/relay.ts](server/src/relay.ts), [src/server/online.ts](src/server/online.ts)): **the server runs every online match.**
- Pairing is as before (quick match queue, or a friend room by code); `Net.quick/host/join` send the account token, so the server knows whose match it is. Seat 0 is whoever made the room or queued first; the meadows keep the seat order everywhere (seat 0 is field 0, on the left in landscape), and `Game.me` says which is this player's (theirs takes the big place in the tall layout, is tagged YOU and gets the full sound).
- Fairy select: each browser sends its cursor and pick (`Net.select`); the server passes the cursor on and accepts a pick only if that fairy is open on the player's server record. Once both have picked it deals the rounds: a seed (which also picks the map, `mapForSeed`) and the round's start (`'round'`), then the countdown.
- `OnlineMatch` (bundled into `dist/server.cjs`, driven 60 times a second by `Relay`) steps its own `RoundSim` with each player's latest controls (a browser sends them, packed by `packControls`, when they change and now and then: `Game.sendControls`), and sends both players every step's controls as it used them (`'f'`, two steps a message; `null` for a frozen step). Each browser plays the very same round from those steps (`Game.stepOnline`: one a step, more to catch up when they pile up, none while waiting), so it shows the server's round exactly, a round trip behind.
- The server decides the knockout (`'end'`, with how many steps the round lasted, so a browser ends it at that very step), the match, and what it earns: `applyOutcome` for each player's side, saved to their record with the history and the match as a replay (`'online'` mode, watched like 2 Players), then `'result'` to each (`Game.onlineResult`). A player who leaves forfeits (a loss for them, a win for the other); then it's back to fairy select for the next match.
- **Bump `NET_VERSION` in [src/core/config.ts](src/core/config.ts) whenever the messages or the simulation change**, so builds that don't match never get paired.

**Rendering.** Rendering reads `Game`/`Field` state and never changes it; the simulation never draws.
- [src/render/renderer.ts](src/render/renderer.ts) (`Renderer`) sets up each frame and composes a meadow layer by layer.
- The drawing itself is plain functions that take the canvas context first, e.g. `drawStar(ctx, …)`. They're grouped by what they draw in `src/render/entities/`: `fairy`, `critters`, `attacks`, `bosses` and `bombs`. HUD icons are in `icons.ts`.
- To draw something new, add a function to the matching entities module and call it from `Renderer.field()`.
- Keep per-frame drawing cheap: never `shadowBlur` on things there can be many of (it costs about a millisecond each on a big canvas). Fireballs other than Reverses are drawn from cached sprites (`flameSprite`, `ballSprite` in `entities/attacks.ts`, painted once at radius 1 and scaled); glows are cached sprites too.
- Behind every meadow is the endless scenery of its map, [src/render/scenery/scenery.ts](src/render/scenery/scenery.ts) (`SkyScenery`, drawn first in `Renderer.field()` from `Field.sceneSeed`, `Field.time` and `Field.mapId`), seen from above at an angle: on an `'islands'` map (Forest, Space) islands with a flat top and a cliff face below float over the clouds (Space's asteroids over nebulae and a twinkling star field, `MapTheme.stars`); on a `'ground'` map (Cave, Desert, Castle, Volcano, whose `'lava'` ground is basalt split by rivers and pools of lava, and Beach, whose `'shore'` ground is sandy islands in the sea, `shoreLand`, with props drawn only on land) solid terrain, painted from world position in seamless bands (`paintGround`: a height field lit from the upper left, shaded through a five-tone ramp with 4×4 ordered dithering), has big props standing on it (`paintProp`) under drifting haze and cloud shadows. Each map's `mood` adds a colour tint, slow light rays, a flock of birds or bats crossing now and then, and giant faint silhouettes passing at the sides; crystals, glowing mushrooms and torches pulse with light (cached glow sprites). The maps are [src/data/maps.ts](src/data/maps.ts) (`MAPS`: Forest, Cave, Desert, Castle, Beach, Volcano, Space), each a `MapTheme` of colours, ground and cliff styles, and weighted props; after the fairies are picked a local match goes to the `mapselect` phase ([map-screen.ts](src/render/screens/map-screen.ts): Random plus a card per map in rows of four (two columns under Random on a phone), each scrolling its scenery live, a locked stage padlocked with the trophies it needs), `Game.beginMatch` fixes `matchMap` (Random rolls one of the open stages per match), online rounds use `mapForSeed(seed)` so both sides agree, and `?map=<id>` forces one. Three parallax layers (far, mid, near) cut into cells of world height whose contents come from (seed, layer, cell) alone, so nothing pops and it never runs out; island, cloud and spire sprites are painted pixel by pixel once ([scenery/paint.ts](src/render/scenery/paint.ts)), at most `PAINT_BUDGET` a frame and ahead of the view, and dropped once long unused; waterfalls, rope bridges and motes are drawn live; near islands keep to the sides and a veil keeps play readable. Painted images listed in [src/data/scenery.ts](src/data/scenery.ts) (`SCENERY_STRIPS`, bottom to top) replace the far layer as one continuous strip. The two meadows look into one world: `Renderer.field` passes each meadow's side and `C.GAP`, so the right-hand meadow sees the stretch of world `GAP` across from the left-hand one (each meadow-wide lane has its own contents, ground is painted from world x via `paintGround`'s `x0`, clouds wrap around the whole world), and terrain, islands and clouds run on from one meadow into the other behind the console. It's decoration only: nothing in it touches the simulation.
- The menu screens share their heading bar, `drawTopBar` in `screens/top-bar.ts` (taller on a phone, where the page's Back tab sits in it).
- A map can have its own monsters: [src/data/monsters.ts](src/data/monsters.ts) (`monstersFor(mapId)`) gives its `MonsterSheet`, and `Renderer.critter` then draws its critters with `drawMonster` (`entities/critters.ts`) instead of puffs, beetles and spinners (the moonseed stays itself). On the Forest a formation of plain critters is slimes or leaf sprites, shelled ones are mushroom buddies, spinners are bees and big ones tree spirits; in the Cave plain ones are cave slimes or wisps, shelled ones crystal bugs, spinners bats and big ones cave mushrooms; in the Desert plain ones are sand slimes or sand foxes, shelled ones desert beetles, spinners scorpions and big ones cactus buds; in the Castle plain ones are crown slimes or will-o'-wisps, shelled ones castle knights, spinners bats and big ones magic books; on the Beach plain ones are sea slimes or starfish, shelled ones pearl clams, spinners seagulls and big ones beach crabs; on the Volcano plain ones are lava slimes or flame wisps, shelled ones lava crabs, spinners fire bats and big ones magma golems; in Space plain ones are galaxy slimes or void octopuses, shelled ones meteor turtles, spinners comet cats and big ones astro robots. `monsterLook` works out which monster and how far it has appeared from position alone (no state, so a mirrored online meadow looks the same): coming in over the top line (`CRITTER_TOP`) or a side wall it plays the sheet's appear frames under the sparkle overlay, then idles, talking or beaming now and then. A gem in the puff colours shows the shots a tougher one takes, and dew bubbles and shells are rings around it. Every map has a sheet; one without would keep the code-drawn critters.
- The HUD, the title and select screens (`screens/`), the backdrop and sprite animation each have their own module. Colours and fonts are in `theme.ts`.

**Data and tuning.**
- Every tuning number is in [src/core/config.ts](src/core/config.ts), imported as `* as C`.
- What a game earns is [src/game/rewards.ts](src/game/rewards.ts) (`applyOutcome`: wins, flawless wins, best chain, Fevers, trophies and new stages, the Endless best, unlocks), the one set of rules the game and the server both use.
- The fairy roster, stats, unlocks and per-fairy attacks/bombs are in [src/data/characters.ts](src/data/characters.ts): Stella (the witch, id `pip`) and Aster (a young knight, unlocked at 600 trophies) fly sprite sheets ([src/data/sprite-sets.ts](src/data/sprite-sets.ts)) and have painted portraits; the others are drawn in code.
- Each map is a stage on a trophy road ([src/data/stages.ts](src/data/stages.ts), `STAGES`: Forest 0, Cave 100, Desert 300, Castle 600, Beach 1000, Volcano 1500, Space 2200 trophies). VS CPU and Online matches win `TROPHY_WIN` or lose `TROPHY_LOSS` (`Game.recordMatch`, into `Progress.trophies`); a stage opens once `Progress.bestTrophies` reaches it, so it never locks again. Each stage has its own `WaveStyle` (weight multipliers on shapes, kinds, moves and exits, and its pressure start and ramp, toughness, extra members, re-forms, big critters, bubbles and pace), which `Field` passes to `rollFormation`, and its own CPU reaction time. Online rounds still take any map from the seed.
- Critter formations are in [src/game/waves.ts](src/game/waves.ts) (members glide in from above, behind the HUD strip, but a formation always sits below `CRITTER_TOP` once it's in; fireballs never start above `FIREBALL_TOP_Y`): each wave is a seeded `FormationSpec` (shape, entry, group movement, optional re-form, exit); each stage has a shape of its own flown on no other map (`WaveStyle.signature`: Forest flowers, Cave stalactites, Desert pyramids, Castle crosses, Beach seashell spirals, Volcano eruptions, Space stars) and keeps mostly to its own mix of the shared ones (`rest`); some formations come down low into the fairy's half, and a `'surround'` ring wheels round the fairy, reaching the bottom of the meadow, as in TSS: a full circle of one-pop critters (about 20), each in reach of the next, so one pop runs right round it. Now and then (more as the round goes on, `WaveStyle.swarm`) a formation is a swarm: 12–18 one-pop critters as a coiled `'snake'` train, a three-row grid or a wide ring, all in reach of one another so a single pop clears the lot. Each formation flies in from off-screen with staggered members, holds its shape while moving as a group, then flies out together. Neighbours are never closer than `formationSpacing` (`shapeSlots` nudges bunched members apart), which leaves a gap you can see between two critters' art (`CRITTER_LOOK_W`) wider than the widest fairy's hitbox; up in the meadow that's still inside one pop's reach (`BURST_RADIUS`, big as TSS's explosions, for the fairy with the smallest pops, `MIN_FAIRY_BURST`) so a chain carries through, and low in her half it's a wide doorway. Pops break fireballs and hurt bosses only out to the old, smaller `BURST_ATTACK_RADIUS`. Positions are in meadow units, so formations look the same at every screen size.
- Saved progress uses localStorage, in [src/game/progress.ts](src/game/progress.ts), and is copied to the database by `Account` (see Docker and the database).

**Audio.** [src/audio/sound.ts](src/audio/sound.ts) synthesizes every effect with WebAudio (the only audio files are the music and the fairies' voices). Both effects and music play through [src/audio/synth.ts](src/audio/synth.ts): two-operator FM patches (`PATCHES`: bell, glock, electric piano, slap bass, brass, lead, pluck, played by `fmNote`) for the bright arcade-FM sound of TSS's era, and a small synthesised room reverb (`makeReverb`) that effects (`wet` in `Sound.out`) and music voices (`Voice.wet`) send into at their own volume. Audio starts only after the first user gesture (`sound.unlock()`). **Voices**: a fairy can have spoken lines ([src/data/voices.ts](src/data/voices.ts), `VOICES` by fairy id: `pick`, `charge` for a level-2 charge shot, `summon` for level 3 with her guardian, `fever`, `hit`, `death`, `win` (each round's winner, `WIN_LINE_DELAY` after it ends, not in Endless) and `reverse` (a volley shot back: `REVERSE_VOLLEY` fireballs reversed within `REVERSE_WINDOW`, at most every `REVERSE_LINE_GAP`); clips in `assets/voices/<fairy>/<event>-<n>.mp3`, inlined like the music; Stella's are cut from one recording, `assets/source/voices/stella-hana.mp3`, whose lines are listed at the top of voices.ts). `Game.voicesFor` reads each meadow's sounds in `drainSfx` (`release` level 2/3, `fever`, `hurt`/`stun`, `reverse`, going down; `roundEndVoice` the win) and `Game.voice` picks a line, never the same one twice running; picking her on fairy select says a `pick` line. `Sound.speak` plays it on its own voice bus (`voiceVolume`, the Voices slider in Settings → Audio, saved with the other volumes) panned to her side: one line at a time per side (a new one is dropped while she's talking, except going down and the win, which cut in), hit lines at most every `HIT_LINE_GAP`; a fairy with no lines is silent. The announcer (`ANNOUNCER` in voices.ts, cut from `assets/source/voices/announcer-claire.mp3` into `assets/voices/announcer/`) says "Choose your champion" when fairy select opens (`Game.start`, not when coming back from map select), and at each countdown the round's call ("Round 1", "Round 2", or "Final round" when both sides are a round from winning; none in Endless) (`announceRound`, from `newRound`), "Ready" at `ANNOUNCER.readyAt` (1.9 s, a beat after the longest call; `announceReady`), and "Fight!" as play starts at `C.COUNTDOWN_TIME` (3 s, the same for online rounds, whose server counts it down too; `announceFight`); each call has its own take of Ready and Fight. The countdown's banners follow the same timeline: the round's call (or Endless's banner) until `callReadyAt`, then READY, then FIGHT! for `FIGHT_BANNER_TIME` as play starts. Fairy select's heading is CHOOSE YOUR CHAMPION. `Sound.speak`'s last argument says what happens while a speaker is still talking: `'drop'` the new line, `'cut'` in, or say it `'after'`. Voices are only sound: nothing in a round depends on them, and a replay seeking ahead says nothing. Effects and music go through their own gains (`volume`, `musicVolume`, saved with mute under `glimmerwing.sound`). The background music is [src/audio/music.ts](src/audio/music.ts): two original synthesized loops (`'menu'`, a gentle F-major lilt on bell, electric piano and pluck; `'battle'`, a bouncy D-major tune on lead, slap bass, piano stabs, brass and drums) on a look-ahead step sequencer whose steps can be single notes or chords; A map can have a recorded track of its own instead ([src/data/music.ts](src/data/music.ts), `MAP_MUSIC`: every map has one now, so the synthesised battle loop is only a fallback), and the menus play a recorded track too (`MENU_MUSIC`, "Chant Royal") in place of the synthesised menu loop, and the fairy and map select screens one of their own (`SELECT_MUSIC`, "Royal Tournament", track `'select'`): MP3s are inlined as data URLs like the images, kept trimmed to loop and re-encoded at 112 kb/s in `assets/music/` (originals in `assets/source/music/`), decoded by `Music.decode` (only the last three decoded tracks are kept, as each is tens of MB; the select track is decoded ahead while the menus play) and looped by `Music.playFile`. `main.ts` picks the music by phase with `sound.playMusic`: none on the title screen (going back to it fades the music out over `FADE_STOP`, 2.5 s; one piece giving way to another fades over `FADE_SWITCH`), the select track on fairy and map select, on the Maps screen the music of the map you're looking at (`Game.browsedMap`, once you've rested on it for `MAPS_MUSIC_DELAY`), the menu track on the other menus, and in a round `roundMusic(game.roundMap)`, the map's own track (`map:<id>`) or the battle loop.

**Settings.** Settings is a `Game` phase (`'settings'`): the canvas draws its sky and the usual heading bar ([settings-screen.ts](src/render/screens/settings-screen.ts)) and the page's ◀ Back tab sits in it as on every menu screen, while the settings themselves are the page's panel (`#settings` in `index.template.html`, placed under the bar by `--bar-h`, which `main.ts` sets from `topBarBottom`; tabs down the left in landscape, across the top on a phone; shown and hidden by `main.ts` as the phase changes; wired by [src/page/settings-panel.ts](src/page/settings-panel.ts)) has Audio (music and effects volume, sound on/off), Display (fullscreen, hide the rival's meadow) and Controls (rebind keys per scheme: one player, or player 1 and 2 sharing a keyboard). Key bindings live in `Settings.keys` (`settings.ts`); [src/input/keys.ts](src/input/keys.ts) has the defaults, labels and `keyMap`, and `Input.setBindings` takes them. Menus always use the fixed keys (arrows, Enter, Z, Esc), and gamepads map to actions directly, so rebinding never strands either.

**Input.** [src/input/input.ts](src/input/input.ts) merges keyboard (the player's own keys, see Settings), gamepad (polled each frame) and touch. The page's prompts switch to whichever device was used last. The page's on-screen buttons (`.touch-ui`) show only on a touchscreen, except the ◀ Back button on the menu screens (the lobby, select, Characters, Profile), which shows on every device so a mouse can leave them. Keys typed into the page's panels (`#lobby`, `#settings`, `#chat`) never reach the game.

## Conventions

- **Imports:** use `./x` within a folder and `@/folder/x` everywhere else, never `../` (ESLint enforces this). The `@/` alias is set in `tsconfig.json` `paths`, and esbuild reads it from there.
- **Types:** `src/types/` holds interfaces and type aliases only, and ESLint enforces it: no runtime exports, and no imports from outside `types/`. Import with `import type { … } from '@/types'`. A type stays private to its module until a second module needs to name it (for example through a public method's signature); then it moves into `types/`.
- Indent with 4 spaces (Prettier and `.editorconfig`); lines are up to 120 characters.
- Every function, class, method, interface, type alias and module-level arrow helper needs a `/** … */` docblock that says what it's for (enforced by `eslint-plugin-jsdoc`). Small lambdas inside a function body and constructors are exempt. Write prose only, with no `{type}` annotations, since TypeScript already has the types.
- Use type-only imports (`consistent-type-imports`), `===`, and an `_` prefix for intentionally unused variables. `console.log` gives a warning; `warn`/`error` are fine.
- The TypeScript config is strict and also turns on `noUnusedLocals/Parameters`, `noImplicitReturns` and `noImplicitOverride`.
- The sprite atlases `assets/witch.png` and `assets/knight.png` (with their `.json`) are generated from `assets/source/` by [tools/extract-witch.py](tools/extract-witch.py) (`<sheet> assets` for the witch, `<sheet> assets knight hair` for the knight: same sheet template, lined up on the hair), and the monster atlases `assets/monsters/<map>.png` and `.json` by [tools/extract-monsters.py](tools/extract-monsters.py) (`python tools/extract-monsters.py <map>` reads `assets/source/<map>-monsters.png`; each sheet's frame layout is in the script's `LAYOUTS`; Python, using PIL, numpy and scipy). Don't hand-edit them.
- ESLint ignores `Claude outputs/`, which holds scratch output, not source.
